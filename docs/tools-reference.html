Audit: what was wrong and what changed

Bugs were confirmed by running the code, not assumed. Design findings are judgements about v1 of the schemas.

A. Confirmed bugs (fixed in code, tests added)

#FindingUser impactFix
A1A "Women's ..." product passed verification for a male shopper (men/women were ignored as stop words).Wrong-gender clothes shown as a match. The worst kind of wrong result for a menswear app.New gender check: rejects women's and kids' items, accepts men's, unisex and unstated.
A2The same product could appear in two outfits (identical top URL reused)."4 outfits" that look like 2. Retries could also re-add products already shown.Cross-outfit de-duplication plus exclude_urls carrying products from earlier rounds.
A3Product had no stock, size or price-freshness fields.User clicks a buy link and the item is sold out. Stale price shown as current.Added in_stock, available_sizes, mrp_inr, fetched_at, extraction. Out-of-stock candidates are rejected.
A4The agent asked "men, women or unisex?"Pointless friction for a men-only app.Gender removed from preferences and prompts; the stylist now needs only budget and occasion.

B. Design findings (applied to the schemas below)

#Finding in v1Change in v2
B1get_budget_split was a tool, but it is pure arithmetic with no network call. Exposing it adds latency, a failure mode and tool-surface for no benefit.cut Now a plain function inside the planner code.
B2get_product_image was an MCP tool, but only the server itself needs it (search and try-on both run server-side).internal Moved to an internal function. Fewer tools to secure and version.
B3search_products and find_products both validated price, category and colour: duplicated, and two places to get it wrong.Clean split: search_products = retrieval, extraction and hygiene (link live, image OK). find_products = requirement matching. confidence removed; provenance fields (extraction, fetched_at) added so the matcher can trust LLM-extracted fields less.
B4generate_image was one polymorphic schema: task enum plus free prompt_ref and free-form variables. A caller could pick any prompt or inject text, and the schema could not enforce "try-on needs 3 images, style preview needs none".Discriminated union: each task has its own required, typed fields. Prompt template is chosen by the server from the task, never by the caller.
B5Image calls take 20-90 s but were modelled as one blocking call. Retries would double-charge.Idempotency key on every costly call; sheet and try-on return a job_id and are polled with get_job.
B6check_link returned a boolean. A bot-blocked 403 and a dead 404 look the same, but mean opposite things.Tri-state verdict: live | dead | unverified, with a reason; soft-404 pages detected.
B7generate_tryon took raw URLs and gave no honesty signal about fit or accuracy.Takes validated product references; output carries a disclaimer and QA detail. Try-on shows how clothes look, not whether the size fits.
B8No cross-cutting contract: no request ID, no schema version, unstructured warnings strings, errors without retry guidance, signed URLs without expiry.One envelope for all tools (see conventions).

C. Product decisions still open

  • Affiliate links. Amazon, Myntra and others pay commission through tracked links. It is the natural revenue model, but needs disclosure on screen and changes how url is produced. Decide before phase 3.
  • Size. Should the user give a size up front so only in-stock sizes are shown? Higher purchase rate, one more question.
  • Photo burden. Exactly 8 photos is high friction. Consider 3+3 minimum with 4+4 recommended, and measure drop-off.
  • Price freshness. Prices change daily. Show "as of" time, or re-check on click.

Conventions for every MCP tool

  • Transport and auth: MCP over streamable HTTP; Authorization: Bearer <JWT RS256> on every call. user_id comes from the token, never from arguments.
  • Request context: every input accepts optional request_id (trace correlation across Mastra, API and MCP). Every output echoes it and includes schema_version.
  • Idempotency: tools that cost money or write data (generate_image, create_character_sheet, generate_tryon) require idempotency_key. A retry with the same key returns the original result instead of charging again.
  • Deadlines: read tools accept deadline_ms; the tool returns what it has by then, marked partial, instead of hanging the conversation.
  • Structured warnings: { "code": "PRICE_OVER_CAP", "message": "...", "count": 2 }, not free strings.
  • URLs to private files are signed and carry expires_at.
  • Audit: each call appends a hash-chained audit row (tool, user, hashed arguments, outcome, latency). Raw images and page text are never logged.
  • Untrusted content: web page text is data, never instructions. Outbound fetches use a domain allow-list, an SSRF guard (no private IPs), a redirect cap, timeouts and size caps.
  • Tool descriptions are written for the model: when to use it, what it returns, what it will not do.

Error envelope

{ "error": { "code": "UPSTREAM_TIMEOUT | NOT_FOUND | INVALID_INPUT | RATE_LIMITED | FORBIDDEN | CAP_REACHED | UNSAFE_REQUEST",
             "message": "human-readable",
             "retryable": true,
             "retry_after_ms": 2000 },
  "request_id": "..." }

Partial success beats failure: a search where 3 of 10 pages fail returns 7 results plus a warning.

find_products + verification built

The graph step that turns the planner's specs into real outfits. Every search result is untrusted: a product is shown only if a deterministic check proves it matches. Code: services/api/src/api/agent/find.py and verify.py.

Anti-hallucination rules

  • Product fields come only from scraped page data. A model never writes or fills in a product.
  • Each verdict records its evidence. No evidence means unknown, never match.
  • Required to be match: price and item. A mismatch on any attribute, including a colour that contradicts the request, rejects the product. Fit, fabric, category and gender may be unknown but not contradicted.
  • Colour rule: colour is looked up in the page's colour field, then the title and description (free, no extra search credits). If neither states a colour, the product is accepted on the strength of the colour-specific search, marked assumed: true, the report gets confidence: "low", and it ranks below confirmed products. The reply to the user says "colour not confirmed by the store".
  • Rejected candidates are returned with reasons, never silently dropped.
  • rank_and_validate re-checks that every outfit item carries a passing report before the user sees it.

Workflow

  1. APICall search_products for every top and bottom in parallel (8 calls for 4 outfits). Today: mock_search, with the same signature.
  2. ValidateFor each candidate run verify_product: price vs cap, item words (synonyms: tee = t-shirt, trousers = pants), category contradiction, colour (page field first, then title/description), gender (reject women's and kids'), and fit / fabric if requested.
  3. ValidateReject out-of-stock candidates and products already used in another outfit (exclude_urls plus this round).
  4. ParsePer item choose the verified candidate with the highest match score, then the highest price under the cap.
  5. ValidateBuild an outfit only if both items verified and top + bottom <= budget_inr; otherwise add an unfilled entry.
  6. StoreThe graph saves outfits, planner notes (from unfilled) and rejected. The planner uses the notes to propose alternatives (max 2 retries).
Measured on 319 real SerpAPI Shopping results (8 menswear queries). Colour is stated in the title for only about 11% of products, so under the old strict rule only 11% passed. With the assumed-colour fallback, 54% are usable: 11% confirmed (high confidence) and 43% assumed (low confidence), giving 10 to 38 usable results per query. Reading the colour from the thumbnail by pixels was only 35% accurate and is not used. Fetching the retailer page (free) can confirm colour, gender and stock: Myntra pages embed them; other retailers are untested. Synonym and colour word lists are small.

search_products phase 3

Retrieval only. Finds candidate men's products for one item and extracts their data. It does not decide whether a candidate matches the request; find_products does. The server always adds "men" to the query.

Input schema

FieldTypeRequiredNotes
itemstringyes"t-shirt", "baggy pants"
category"top" | "bottom"yes
colorstringyes"light blue"
max_price_inrintegeryesUsed to bias the query and drop obvious misses
fit, fabricstringno
retailersstring[]noSubset of the allow-list; default all
exclude_urlsstring[]noSkip products already shown
limitintegernoDefault 10, max 20
deadline_msintegernoReturn partial results by this time. Default 12000
request_idstringno

The first six fields are the existing ItemSpec. There is no gender field by design.

Output schema

{
  "schema_version": "1",
  "request_id": "...",
  "results": [
    {
      "title": "Men's Light Blue Oversized Cotton T-Shirt",
      "retailer": "Myntra",
      "price_inr": 899, "mrp_inr": 1499,
      "url": "https://www.myntra.com/...",
      "image_url": "https://<our-storage>/products/ab12.jpg",
      "color": "light blue",
      "description": "...",
      "attributes": { "color": "Light Blue", "fabric": "Cotton", "category": "top", "gender": "men" },
      "in_stock": true, "available_sizes": ["M","L","XL"],
      "extraction": "json_ld",            // json_ld | open_graph | llm_fallback
      "fetched_at": "2026-10-02T09:15:00Z"
    }
  ],
  "query_used": "light blue oversized cotton t-shirt men",
  "from_cache": false,
  "partial": false,
  "warnings": [ { "code": "IMAGE_FAILED", "message": "2 products dropped: image did not load", "count": 2 } ]
}

results[] is the Product model. Empty results is a valid answer, not an error.

Workflow

  1. GuardVerify JWT, rate-limit per user, validate input; reject retailers outside the allow-list.
  2. ParseBuild the query: "{color} {fit} {fabric} {item} men", normalised (lowercase, de-duplicated words).
  3. StoreCache lookup by hash of the normalised arguments (TTL about 6 hours). A hit returns at once with from_cache: true.
  4. APICall the search API (Tavily or SerpAPI), restricted to allow-listed domains, max_results about 2x limit. Retry 429 / 5xx with backoff (max 2 retries, 8 s timeout).
  5. GuardDrop hits whose host is not on the allow-list or whose URL is in exclude_urls.
  6. APIFetch each product page concurrently (5 s timeout, 1 MB cap, SSRF guard, max 3 redirects), respecting deadline_ms.
  7. ParseExtract fields in priority order: (1) JSON-LD Product / Offer; (2) Open Graph and product:* meta tags; (3) fallback LLM extraction from the visible text with a strict schema and the instruction that the text is untrusted data. Record the source in extraction.
  8. ParseNormalise the price (strip the rupee sign, commas, "MRP"; ranges take the selling price; integer INR). Read stock and sizes where the page states them. Reject unparseable prices.
  9. ValidateHygiene only: link live (check_link), not a soft-404, image downloads and passes checks. Failures are dropped with a warning. Requirement matching is not done here.
  10. StoreCache images in our storage (internal fetch_product_image), cache the result list, append the audit row.
  11. Return the output.

check_link phase 3

Confirms a buy link is live and still points at an allowed retailer. Used inside search_products and again just before outfits are shown.

Input

FieldTypeRequired
urlstring (URL)yes
request_idstringno

Output

{ "schema_version": "1", "url": "...", "final_url": "...",
  "verdict": "live | dead | unverified",
  "reason": "ok | not_found | gone | soft_404 | bot_blocked | timeout | redirected_off_domain | not_https",
  "status": 200, "domain_allowed": true, "checked_at": "2026-10-02T09:15:00Z" }

unverified (for example a 403 from bot protection) means "we could not tell". The agent keeps the product but does not claim it is confirmed live. dead removes it.

Workflow

  1. GuardParse the URL; allow only https; host must be on the allow-list.
  2. GuardResolve DNS; reject private, loopback and link-local addresses.
  3. APIHEAD (4 s timeout); on 405 / 403 fall back to GET reading only the first bytes.
  4. ValidateFollow at most 3 redirects, re-checking allow-list and SSRF rules at each hop.
  5. ParseSoft-404 check: a 200 page whose title or text says "not found / no longer available" is dead with reason soft_404.
  6. Map the outcome to verdict and reason and return.

generate_image phase 3 / 9

The one place images are generated. The provider (OpenAI now, any other later) and model are config, so swapping never touches the agents. Used directly for style previews and flat-lays; the character-sheet and try-on tools call it internally.

Input: a discriminated union on task

Each task has its own required fields. The server picks the prompt template from the task. The caller cannot pass a prompt or free-form variables.

taskRequired fieldsNotes
style_previewstyle_id, style_name, style_descriptionNo input images. Output is a clothing-only mood board. Pre-generated for the library.
flatlaytop_image_id, bottom_image_idComposes one outfit picture from cached product images.
character_sheetcloseup_ids[4], fullbody_ids[4]Normally reached through create_character_sheet.
tryonsheet_id, top_image_id, bottom_image_idNormally reached through generate_tryon.

Common fields: idempotency_key (required), request_id, size (optional, default per task). All ids are image ids already in our storage and owned by the caller; URLs are not accepted.

Output

{ "schema_version": "1", "request_id": "...",
  "status": "succeeded | running | failed",
  "job_id": "job_5c1e",               // present when status is running
  "images": [ { "image_id": "gen_71ab", "url": "https://<storage>/generated/71ab.png",
                "expires_at": "2026-10-02T10:15:00Z", "width": 1024, "height": 1536 } ],
  "provider": "openai", "model": "<from config>", "prompt_version": "tryon.v1",
  "cost_estimate_usd": 0.04, "latency_ms": 18400 }

Workflow

  1. GuardVerify JWT; check idempotency_key (a repeat returns the stored result); per-user daily cap and rate limit (CAP_REACHED); for tasks using personal photos confirm active consent.
  2. StoreLoad input images by id and confirm each belongs to the caller (FORBIDDEN otherwise).
  3. ParseLoad the server-side prompt template for the task and fill it from the typed fields.
  4. GuardSafety rules per task: clothing swap only for try-on, no body alteration, nothing sexual; violations return UNSAFE_REQUEST.
  5. APICall the ImageGenProvider adapter: generate(task, prompt, images, size). The adapter hides provider differences (multipart versus JSON, base64 versus URL). Long timeout (about 90 s); one retry on 5xx. Slow tasks run as a job.
  6. ParseDecode the response into bytes.
  7. ValidateOutput decodes, size is as expected; provider safety flags surface as errors, never ignored.
  8. StoreSave to object storage, record cost and latency, write the result row.
  9. Append the audit row (ids and hashes only) and return.
The image model in your notes could not be verified by me. Its exact ID, input-image limits and API shape must be confirmed before phase 9; only the adapter should need to change.

  1. GuardJWT; consent active; daily cap; idempotency key.

  5. StoreSave the sheet; set review_required: true until the user confirms.
  6. Poll with get_job. A durable Mastra run keeps this alive if the app closes.

Workflow

  1. GuardJWT; sheet exists, confirmed and owned; consent active; daily cap; idempotency key.
  2. APIInternal fetch_product_image for the top and the bottom (allow-list, validation, caching).
  3. APIgenerate_image with task=tryon: sheet + top + bottom, keeping face, body and pose and changing only the clothing.
  4. AIVision QA: right garments, right colours, face still matches the sheet. Output score, booleans, issues[].
  5. ValidateOn QA failure retry (max 2, feeding issues into the prompt). Retries do not count against the daily cap.
  6. StoreSave the best attempt with its QA score. If QA never passes, return the best result with the issues so the UI shows "may not be exact".
