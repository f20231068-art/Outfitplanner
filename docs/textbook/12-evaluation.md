## 12.1 Why evals

Traditional software is deterministic: the same input gives the same output, so a unit test can say pass or fail. AI components are **probabilistic and open-ended**: the same prompt can produce different outputs; "correct" may be a matter of degree; a change that improves one behaviour quietly breaks another; and nobody can eyeball a thousand outputs after every edit.

**Evals are tests for AI systems.** They answer three questions that determine whether you can ship and keep improving:

1. **Does it work?** (Does the system keep the promises we made?)
2. **Did this change make it better or worse?** (Prompt, model, retrieval, code.)
3. **Where does it fail?** (So we know what to fix next.)

Without evals, teams argue from anecdotes ("it felt better"), fear every change, and discover regressions from customers. With evals, you can swap models, rewrite prompts and refactor code *confidently*. **Eval-driven development** is to AI engineering what test-driven development is to software: write the failing case first, then change the system until it passes, then keep the case forever.

A caution in the other direction: **an eval measures only what it measures.** A green dashboard is a claim about *specific* behaviours on *specific* data (Section 12.9).

## 12.2 Levels of evaluation

| Level | Unit under test | Example | Typical cost |
|---|---|---|---|
| **Component** | one prompt/schema, one retriever, one verifier | `verify_product` against labelled products (Chapter 11); a prompt's extraction accuracy | cheap, fast, run constantly |
| **Pipeline / step** | several components | planning + search + verification for a spec | medium |
| **End to end (session)** | the whole product as a user sees it | a scripted shopper conversation from first message to outfits | slow, costs real calls |
| **Online** | production traffic | rates of errors, refusals, thumbs-down, purchase clicks; sampled judged transcripts | continuous |
| **Human review** | expert reading real outputs | weekly review of 30 conversations | expensive, highest validity |
| **Adversarial / red-team** | safety and robustness | prompt injection, jailbreaks, PII extraction, abuse | targeted |
| **Benchmarks** | general model capability | public leaderboards | only for model *selection*, never a substitute for your task |

A healthy practice has **many cheap component evals** (the base of a test pyramid), **a modest end-to-end suite**, **human review of samples**, and **online monitoring**.

## 12.3 Datasets: the part that matters most

The quality of an eval is the quality of its **dataset** (cases plus the expectation for each).

### Where cases come from

* **Real usage** (the best source): logs of actual user requests (with consent and privacy handling), support tickets, failed conversations.
* **Domain experts**: "what would a stylist expect for this request?"
* **Hand-written edge cases**: empty input, contradictory requests, very small budgets, very large budgets, unusual occasions.
* **Synthetic cases**: generated by a model from templates or documents, then **reviewed by a human**. Good for coverage; risky if used unreviewed (the generator's blind spots become the eval's blind spots).
* **Every production failure becomes a new case.** The dataset is a living regression suite.

### Coverage: think in categories

For this app, the 13 cases are organised deliberately:

* **Complete requests** (9): budget and occasion given, from ₹1,500 to ₹15,000 and across occasions (college, office, party, wedding, casual, gym, travel): the agent should go straight to styles and deliver.
* **Incomplete requests** (4): `missing-budget`, `missing-occasion`, `missing-both`, `vague-no-numbers`: the agent must ask for **exactly what is missing** and then continue (with scripted `answers`).

What is *not* covered yet (honest gaps): non-English or code-mixed input, nonsense budgets, prompt-injection attempts, follow-up turns ("make it cheaper"), repeat rounds in one conversation, concurrent users. A coverage matrix (rows: scenario types; columns: cases) makes gaps visible.

### Expectations ("ground truth")

Each case carries what should be true, expressed as **properties** instead of exact text: `expect.budget` (every outfit at or under this), `expect.asks` (which fields the agent should ask about), `expect.outfits` (default 4), plus `answers` (what the simulated shopper replies) and `style` (which card they pick). **Property-based expectations survive non-determinism**: two different but correct outfit sets both pass.

### Splits and leakage

* Keep a **held-out test set** you never tune prompts on; tune on a **dev set**. Otherwise you measure memorisation.
* Avoid **contamination**: if your examples appear in your few-shot prompt or fine-tuning data, the eval is meaningless.
* **Version the dataset** (in git) and record which version produced which result.
* **Size**: tens of cases catch gross regressions; hundreds are needed to detect small improvements (Chapter 5's confidence-interval math: with 13 cases, "13/13 passed" is consistent with a true pass rate as low as ~77%).

## 12.4 Scoring methods

### 1. Deterministic, rule-based scorers (preferred when possible)

A scorer is a function `(case, output) → score in [0,1] + reason`. For properties that can be stated precisely, **code is the best judge**: free, instant, perfectly repeatable, and it can run on every case and every production sample. This project's twelve scorers (`apps/mastra/src/mastra/scorers/rules.ts`) are all of this kind:

| Scorer | Kind | Checks |
|---|---|---|
| `outfitCount` | gate | exactly the expected number (default 4) delivered; score = n / expected |
| `withinBudget` | gate | every outfit total ≤ `expect.budget` |
| `allItemsVerified` | gate | every product carries `verification.is_match === true` |
| `menswearOnly` | gate | no women's/kids' words in titles (regex) and no gender mismatch in the report |
| `noDuplicateProducts` | gate | each `product_id` (or url) appears once |
| `priceIntegrity` | gate | `total_inr === top.price_inr + bottom.price_inr`, prices > 0 |
| `askedOnlyWhatIsMissing` | gate | set comparison of expected vs actual asked fields: score = |both| / |union| (precision *and* recall in one number) |
| `noBackendErrors` | gate | no error outcome; 0.5 if any search failed |
| `garmentVariety` | soft | distinct (top, bottom) garment pairs / outfits |
| `confirmedColourShare` | soft | share of outfits with `confidence: high`; **informational: low is honest, not wrong** |
| `latency` | soft | 1.0 up to 60 s; decays linearly to 0 at 180 s |
| `callEfficiency` | soft | penalises more than ~8 model calls or ~16 searches (a loop or waste detector) |

Design observations:

* **Scores in [0, 1] with a human-readable `reason`**: failures explain themselves ("2 outfit(s) over the ₹4000 budget (max ₹4,310)").
* **Soft and hard signals are separated** (Section 12.5).
* **Scorers are independent and tiny**, each testable on its own (`rules.test.ts`).
* They measure **properties of the output and the process** (calls, time), not just the answer: efficiency and latency are product requirements too.

### 2. Model-graded evals ("LLM-as-judge")

For qualities no rule can capture ("do these colours look good together?", "is the explanation helpful and accurate?", "did the answer stay faithful to the retrieved text?") use another model as a grader. Useful, but it is itself an unreliable instrument that must be **validated**.

**How to do it well:**

* **Rubric, not vibes.** Define criteria with anchored scale points: *"5 = all four outfits have a clear palette logic and suit the occasion; 3 = two outfits clash or ignore the occasion; 1 = ..."*. Ask for **reasoning first, then the score** (a structured output with `reasoning` before `score`).
* **Prefer narrow binary or 3-point judgments** over fuzzy 1-10 scales; they are more consistent.
* **Pairwise comparison** ("which of A or B is better?") is usually more reliable than absolute scoring. **Randomise the order** to cancel **position bias**.
* **Known biases**: prefers longer answers (verbosity bias), prefers its own model family's style (self-preference), sensitive to formatting, can be swayed by confident tone. Counter with rubrics, length controls, using a *different* and *stronger* judge model, and multiple samples.
* **Give the judge references** when you have them (the ground truth, retrieved context).
* **Calibrate against humans**: label 50-100 outputs by hand, run the judge, measure agreement (Cohen's κ, or simple accuracy against the labels). Only trust the judge at the agreement level you measured, and re-check when you change the judge model or prompt.
* **Keep the judge out of the loop it grades**: do not optimise a prompt directly against a judge you never validated (Goodhart's law: a measure that becomes a target ceases to be a good measure).
* **Cost**: judge calls cost tokens; sample production traffic rather than judging everything.

A small judge schema:

```python
class TasteVerdict(BaseModel):
    reasoning: str = Field(description="2-3 sentences explaining the verdict before giving it")
    colour_coherence: Literal["good", "acceptable", "clashing"]
    occasion_fit: Literal["good", "acceptable", "poor"]
    would_a_stylist_recommend: bool
```

*The project lists this as not built ("a model-based or human taste judge: no LLM quota left to build/test it").* That is the honest next step for measuring **quality**, as distinct from **guarantees**.

### 3. Human evaluation

Ground truth for subjective quality. Use **clear instructions**, **two raters per item** on a subset, **inter-annotator agreement**, and a simple tool (spreadsheet or annotation UI). Review a **random sample** weekly, plus **all low-confidence and thumbs-down cases**. Human labels also train and validate your LLM judge.

### 4. Implicit and behavioural signals (online)

* Thumbs up/down, "regenerate", edits, abandonment, follow-up message rate.
* **Task success proxies**: in this app, *Buy* clicks, link-verdict `live` rate, proportion of conversations that reach outfits.
* **Cost and latency per outcome**.
* Beware **selection bias** (only some users give feedback) and **delayed outcomes**.

### 5. Similarity metrics

For tasks with a reference text, classic metrics (BLEU, ROUGE, edit distance) are weak for open-ended generation; **embedding similarity** to a reference is better but coarse. Use them for narrow tasks (translation, summarisation baselines), not as your only signal.

## 12.5 Hard gates versus soft signals

The report in `apps/mastra/src/evals/report.ts` encodes a distinction every eval suite needs:

```ts
export const COLUMNS = [
  { key: 'count',    label: '4 outfits', rule: rules.outfitCount,         gate: true  },
  { key: 'budget',   label: 'budget',    rule: rules.withinBudget,        gate: true  },
  ...
  { key: 'variety',  label: 'variety',   rule: rules.garmentVariety,      gate: false },
  { key: 'colour',   label: 'colour ok', rule: rules.confirmedColourShare, gate: false },
  ...
]
export function gateFailures(rows) {                   // any gate scoring below 1.0 is a failure
  return rows.flatMap(r => COLUMNS.filter(c => c.gate && r.verdicts[c.key].score < 1).map(...))
}
```

* **Gate (hard guarantee)**: a promise the product makes absolutely: *must be 1.0 for every case*; otherwise the run **exits with code 1**, so CI fails. Examples: budget, men's only, verified items, correct totals.
* **Soft signal**: a quality indicator you track and discuss but that does not block a release: variety, confirmed-colour share, speed, call counts.

Why the split matters: if every metric is a gate, the suite is too brittle and people disable it; if none are, it never stops a bad release. **Gate on promises; trend the rest.** The exit-code convention (0 pass, 1 gate failure, 2 harness crash) lets any CI system consume the result.

## 12.6 The harness in this repo, end to end

### Architecture

```
apps/mastra/src/
  evals/cases.ts            13 cases (the dataset)
  evals/run.ts              runner: queue, concurrency, report, exit code
  evals/report.ts           columns + gate rule (separate so they can be unit-tested)
  mastra/workflows/stylist-session.ts   a Mastra workflow: one step "converse", scorers attached
  mastra/stylist/session.ts runSession: plays the shopper (asks, answers, picks a style)
  mastra/stylist/client.ts  StylistApi: login/register, create conversation, send message (SSE), retry on 429
  mastra/stylist/sse.ts     SSE reader
  mastra/scorers/           rules.ts (pure functions) + index.ts (Mastra wrappers)
  mastra/audit/             hash-chained audit + exporter
  mastra/index.ts           Mastra instance: storage, observability, scorers, workflows
```

### Black-box testing of the real API

The harness is a **client of the running API**, exactly like the web app: it signs in (creating `eval-bot-N@example.com` accounts on first use), opens a conversation, sends the first message, **reads the SSE stream**, answers questions the agent asks, **chooses a style** from the cards the agent sends, and collects the outfits. Because it uses only the public HTTP contract:

* it cannot accidentally depend on internals;
* it tests auth, rate limits, streaming, persistence and the agent *together*;
* it would work unchanged against a staging or production deployment.

### The simulated shopper (`runSession`)

* Up to `MAX_TURNS = 6` turns.
* On an `interrupt` of type `ask`, it detects *which field* the question is about (`fieldAsked` looks for "budget" or "occasion" in the question text), records it in `asked`, and replies with the case's scripted `answers[field]`. **If there is no scripted answer, the conversation stops there, which is itself a result** (the agent asked for something the case did not expect).
* On `choose_style`, it picks by index or by id/name (default: the first) and sends the style id.
* On `status` events it records stage timings; on `done` it records the outcome and call counts; on `error` it records the message.

### Respecting the system under test

* **Cases spread across a pool of 4 eval accounts** (hash of the case id modulo `EVAL_USERS`), so the API's **per-user rate limits stay switched on**: *"which we deliberately do not weaken for tests."* A test environment that disables protections tests a different system. Instead the harness is polite: a 429 triggers sleeping for `Retry-After` (+250 ms, up to 3 attempts), safe because *a rate-limited request was refused before processing*, so repeating cannot double anything.
* **Concurrency is limited** (default 2) to avoid self-inflicted overload.
* **Config loading is least-privilege**: the Mastra app reads only an allow-list of variables from the repo `.env` (`STYLIST_API_URL`, `EVAL_*`, `OTEL_*`...). *"Mastra never needs your API keys, so it never loads them."* A neat application of least privilege to a developer tool.

### Mastra's role

**Mastra** is a TypeScript framework for agents, workflows, evals and observability (Chapter 15). Here it provides:

* a **workflow** `stylistSession` with a single **step** `converse`, which runs the session and returns the result;
* **scorers** (`createScorer(...).generateScore(...).generateReason(...)`) attached to the step with `sampling: {type: 'ratio', rate: 1}` (score **every** run, since they are free), so each run is scored automatically and the scores show up in Studio and in the audit chain;
* **tracing**: the workflow run is a span; each backend stage reported by the API (`status` events with `duration_ms`) becomes a **child span, back-dated by its duration**, so the trace shows real step lengths;
* **trace propagation**: each request carries a W3C `traceparent` built from *Mastra's* trace id, and the API adopts it, so **one id links the eval trace, the API's logs and the audit-log entries** (Chapter 13);
* **storage** in a local libSQL file, and a second, hash-chained **audit** record of every workflow run, step, model call and score (Chapter 22).

### Running it

```bash
python scripts/init_observability.py && docker compose --profile observability up -d
(cd services/api && BACKEND_MODE=demo uv run uvicorn api.main:app --port 8000)
npm run eval -- --concurrency 3          # all 13 cases
npm run eval -- --only college-4000,missing-budget
npm run audit:verify
npm run studio                            # http://localhost:4111
```

Output is a table of 12 columns per case, an AVERAGE row, then either `All hard guarantees held for every case.` or a list of `GATES FAILED`. Exit code is 1 on any gate failure.

## 12.7 What this eval proves, and what it does not

**Demo mode** (`BACKEND_MODE=demo`) replaces the language model with a deterministic script (`ScriptedLLM`) and the search tool with mock products (`mock_search`, including a wrong-colour decoy). Consequences:

* A perfect score proves the **plumbing and the guarantees**: budget enforcement, verification, streaming, database persistence, rate limits, tracing, auditing. Those can regress when someone edits code, and the eval will catch it **for free, in seconds, with no quota**.
* It proves **nothing about the real model**: it cannot tell you whether the model extracts budgets correctly from messy phrasing, plans good outfits, or follows the prompt; nor whether the real search returns usable results.
* It cannot judge **taste**.

To evaluate the real thing, run against `BACKEND_MODE=live`: about 6 model calls and 8-16 searches per case, so 13 cases need ~80 model calls (the free model allows 50 a day), and spend search credits. **Budget evals like any other resource**: run the cheap offline suite on every commit; run the live suite nightly or before releases on a sampled subset; keep a small "smoke" subset for quick checks.

### Honest statistics

Thirteen cases is a **smoke test and a regression net**, not statistical evidence of quality. Recall Chapter 5: 13/13 gives a 95% lower bound near 77% on the true pass rate; the more *categories* of failure you cover matters more than the count. Grow the dataset from real failures.

## 12.8 Evals in the development loop and in CI

**The loop:**

1. Observe a failure (a user report, a trace, a human review).
2. **Add a case** that reproduces it (it should fail).
3. Change prompt/code/model.
4. Run the suite: the new case passes, and **nothing else regressed**.
5. Merge, keep the case.

**In CI (Chapter 28):**

* Offline deterministic evals and unit tests on every pull request.
* A **live eval** on a schedule, with budgets and alerts.
* **Compare to baseline**: store the previous run's scores and flag drops beyond noise (using repeats and thresholds).
* **Artifacts**: save the report and traces for failed runs.
* **Flaky evals** (pass/fail changes without code changes) are bugs in your harness or sign of high variance; fix by repeating runs, relaxing to rates, or removing non-determinism.

**Before swapping a model or prompt**: run the full suite on both, compare scorecards, review a sample of disagreements by hand, then decide. *Model upgrades are the most common cause of silent regressions in production AI features.*

## 12.9 Pitfalls

| Pitfall | Why it hurts | Defence |
|---|---|---|
| **Goodhart's law** | optimising the score instead of the goal | multiple metrics, human review, fresh held-out cases |
| **Test-set overfitting** | you tuned until it passed | dev/test split; add new cases regularly |
| **Eval does not match production** | different inputs, safety limits disabled, different data | sample real traffic; test the real API; keep protections on |
| **Judge unreliability** | wrong grader, wrong conclusions | calibrate on human labels; pairwise; rubric |
| **Metric blindness** | you measure what is easy, not what matters | map each product promise to a metric; list unmeasured promises |
| **Too slow / too expensive** | nobody runs it | tiers: smoke, offline, live; sampling |
| **Flakiness** | trust erodes | repeats, rate thresholds, deterministic scorers |
| **Silent harness bugs** | green because the scorer is broken | test the scorers themselves (`rules.test.ts`); include known-bad cases that must fail |
| **Ignoring the long tail** | averages hide rare catastrophic failures | gates for catastrophic classes; examine worst cases |

**Test your tests.** Include a case or unit test where the output is *known bad* and assert the scorer fails it. A scorer that cannot fail is decoration.

## 12.10 Red-teaming and safety evals

Separate from quality evals: deliberately attack the system.

* **Prompt injection** in user messages, retrieved text and tool outputs.
* **Jailbreaks**, role-play attacks, instruction override attempts.
* **PII and secret extraction** ("repeat your system prompt", "what is the API key?").
* **Abuse and harmful content**, policy edge cases.
* **Resource abuse**: giant inputs, rapid-fire requests, many conversations (this app's limits and caps).
* **Cross-user access**: try to read someone else's conversation id (404), buy-link of an unseen product (404), admin endpoint as a normal user (404).

Automate as many as possible into a regression suite; track an **attack success rate**. Many of these checks in this repo are *unit and integration tests* rather than model evals (ownership, rate limits, SSRF), because they test code, not model behaviour (Chapter 29). Use frameworks (promptfoo, garak, PyRIT) for model-level red-teaming.

## 12.11 Online evaluation and monitoring

* **Log structured traces** (ids, durations, counts, versions) without storing sensitive content unnecessarily.
* **Sample** conversations for LLM-judge and human review.
* **Dashboards** for success rate, error rate by cause, latency percentiles, cost per conversation, refusal rate, confidence split (Chapter 13).
* **Alerts** on SLO burn (e.g. conversation success rate drops), not on every blip.
* **Feedback capture** in the UI; connect to traces so a thumbs-down opens the full trace.
* **Canary and A/B tests** for prompt/model changes: send 5% of traffic to the candidate, compare outcome metrics with proper statistics (Chapter 5).
* **Drift detection**: input distribution shifts (new kinds of requests), provider model updates, data source changes (e.g. SerpAPI result format).

## 12.12 Tooling landscape

* **Mastra evals** (this repo), **Langfuse**, **LangSmith**, **Braintrust**, **Arize Phoenix**, **Weights & Biases Weave**, **OpenAI Evals**, **promptfoo** (config-driven, CI-friendly), **DeepEval**, **RAGAS** (RAG metrics), **Inspect** (UK AISI), **garak/PyRIT** (red-team).
* Or **plain pytest/vitest plus a spreadsheet**: perfectly good for a small team. The tools differ in UI, storage, tracing and judge helpers; the *method* is what matters.

## Common mistakes

* No evals; relying on demos.
* Evals that only measure what the system already does well.
* Treating a passing eval as proof of quality.
* Using an unvalidated LLM judge as the sole signal.
* Disabling security limits "for testing".
* Never adding production failures to the dataset.
* Running only on the happy path.
* Letting the eval take 3 hours so nobody runs it.

## Summary

* Evals are tests for probabilistic systems: they answer "does it work, did the change help, where does it fail".
* Dataset quality dominates: real cases, coverage, property-based expectations, held-out sets, versioning, growth from failures.
* Prefer deterministic scorers; add validated LLM judges and human review for subjective quality; use online signals for ground truth.
* Separate **gates** (promises) from **soft signals** (trends); fail CI on gates.
* The repo's harness drives the real API as a black box, keeps protections on, links traces and audit by id, and honestly states its demo-mode limits.
